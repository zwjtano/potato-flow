# AI 调用机制代码审查

## 2026-08-24 10:07

### 审查结论

当前实现已从“功能可用但请求不可控”进入“请求有统一边界”的阶段，但仍未完成 Prompt 模块化、应用级结果缓存和单母图封面。以下结论按风险排序。

### 已处理

1. **物理请求漏记和 RPM 失控**：SDK 重试、思考参数降级、JSON 回退现在均经过统一物理调用边界；每次调用重新获取跨进程 RPM 槽位并独立记账。
2. **官方缓存能力未启用**：新增端点/模型能力策略，对官方 GPT-5.6 使用显式断点、TTL 和稳定缓存键；兼容端点默认不发送专用字段。
3. **动态房间规则破坏前缀**：标题与简介的房间偏好已迁入用户负载 `editorial_preferences`。
4. **缓存成本不可见**：账本新增 `cache_write_tokens`，保留 `cached_tokens`，并记录缓存模式、缓存键和治理等待时间。
5. **任务归因过粗**：`ai_runs` 新增 `job_id` 与 `job_purpose`；元数据、标签分区和两个封面不再只有同一个 task_id。
6. **文本调用路径分裂**：字幕翻译和字幕质检已改用统一调用层；智能分段继续复用同一层并补齐能力配置。

### 仍需改进

#### P1：大型系统提示词仍违反渐进式披露

元数据 system prompt 仍包含较多仅对 DOTA2 有效的规则。即使缓存命中能降低费用，它仍增加首个请求 token、模型注意力竞争和维护风险。应提取为版本化、可组合的领域片段，并通过结构化上下文决定是否加载。过期的 TI 2026 专用片段已经删除。

#### P1：缺少应用级结果缓存

Prompt Caching 只降低重复前缀成本，不会跳过模型推理。内容画像、标签和分区等低温度确定性任务仍应按 `prompt_version + model + normalized_input_hash` 缓存最终结果；手动重生成和模型版本变化必须绕过或失效。

#### P1：模型路由仍过于粗糙

所有文本任务基本继承同一个全局模型。高频证据压缩、标签分类和最终标题编辑对质量/成本的要求不同，应定义场景级模型能力和 token 预算，避免用最高价模型完成简单批次工作。

#### P1：双封面仍是两次独立生图

当前 16:9 与 4:3 仍会分别调用图像模型。下一步应先建立 Master Art 安全区、主体检测和程序化文字渲染评测，再把 4:3 改为本地派生；不建议直接上线跨录播网格裁切。

#### P2：SQLite 治理器需要仪表盘和长期维护策略

当前滑动窗口在每次获取槽位时清理 60 秒以前的事件，数据量可控，但还需要在 UI 展示等待时间、峰值 RPM 和按 provider bucket 的健康状态。异常时采用 fail-open，以避免本地数据库故障阻断投稿；生产部署可选择 fail-closed。

### 安全与隐私

- 调用账本和治理器不保存 API key、原始字幕、弹幕、提示词或模型输出。
- provider bucket 使用端点与 API key 摘要，缓存键只包含稳定提示词摘要和非敏感场景名。
- 不读取、复用或转发 Codex/ChatGPT 登录 token。
- 兼容端点的缓存能力默认关闭，避免把不支持的字段发送给未知供应商后形成额外付费重试。

### 建议的发布后验证

选择同一房间、相同 Prompt 版本的 3 个连续录播，比较发布前后：

1. 首批请求后的 `cached_tokens / input_tokens`；
2. `cache_write_tokens` 是否只在预期的缓存预热阶段出现；
3. 每个 `job_purpose` 的逻辑/物理请求数；
4. `physical_request_count / logical_request_count` 重试放大率；
5. 一分钟窗口的实际请求数是否不超过配置；
6. 标题、时间线事实正确率是否与基线持平。

### 发布前复审结论

未发现阻止 v1.6.127 发布的代码问题。

- 删除 TI 模式后再次执行未定义符号检查，清理了 `bridge.py` 中残留的赛事封面、选手选择、队标覆盖和旧测试；运行时代码已不再导入或调用 TI 2026、Liquipedia 或 OpenDota 专用模块。
- LLM 统一边界、AI 字幕阶段、合集 20080 幂等语义和通用封面路径均通过全量回归：845 个主测试（26 跳过）与 331 个应用测试，共 1176 个测试无失败。
- Ruff 致命错误/未定义符号检查通过，MkDocs 严格构建通过，`git diff --check` 无空白错误。

### 发布后仍需验证的风险

1. Prompt Cache 是否真实命中必须以生产账本的 `cached_tokens` 为准；不同兼容服务不能假设支持 OpenAI 专用缓存字段。
2. 当前限流器治理文本模型的物理 RPM，尚未统一覆盖图像和 ASR 的独立速率/预算池，也不是 TPM 限流器。
3. AI 字幕已进入任务流程并复用统一文本分析层，但语音识别本身仍由现有 ASR provider 执行；其音频分钟数和费用需要在下一版纳入统一成本看板。
4. 应用级结果缓存、分场景模型路由、可组合 Prompt Registry，以及“单母图派生 16:9/4:3”仍是下一阶段工作，不能把本版的 Prompt Cache 视为请求次数优化已经完成。

## 2026-08-24 11:52

### v1.6.128 Control Plane / Evidence / OCR 发布前复审

结论：未发现阻止发布的问题。

- LLM 4 Profile 的场景过滤、旧配置关闭语义、Key 更换后的电路隔离和 429 自动切换均有单元/集成测试；依赖注入客户端保留原 JSON → text 补救语义。
- 图片 Profile 只注册 `openai-compatible` Adapter；生成与参考图编辑在真实物理请求边界逐 Provider 记账，额度/鉴权/容量异常进入共享熔断后切换。未实现的 Adapter 不会进入有效路由。
- ASR `free_pool` 先经过能力与 `free_only` 匹配，再执行 Groq/Cloudflare 音频额度预留；已有字幕仍在 ASR 之前短路。
- Evidence FTS 使用参数绑定；用户输入非法 FTS 表达式时退化为有界 LIKE。Transcript 重试会在事务中替换同录播索引，不产生重复段。
- OCR 将跨录播的 `frame_sha256 + model_version` 推理缓存与每录播 frame/evidence 身份分离，避免相同画面串任务；固定单线程、最大候选帧和非阻断 warning 控制资源风险。
- 设置页的 8 个 Provider Key 均进入敏感字段掩码；熔断、额度和结果缓存只保存不可逆摘要或结构化结果，不读取 Codex/ChatGPT 登录 token。
- 流程列表新增 `evidence` 与 `visual_evidence`，后端初始化、排序、前端文案和状态产物保持一致。

验证：根测试 875 项（26 跳过）通过，应用测试 331 项通过，共 1206 项无失败；Ruff `E9/F63/F7/F82`、`git diff --check` 与 MkDocs strict build 通过。

已知但不阻止本版发布的边界：

1. OCR 默认关闭，首次启用会加载本地 RapidOCR/ONNX Runtime 模型；发布后应测量 CPU 时间、帧存储增长和 `useful_visual_evidence_rate`。
2. 当前视觉候选已接固定周期与弹幕峰值；ASR 触发短语、GSI 事件和 CandidateEvent 自动融合仍属于下一阶段。
3. Gemini Image native、Tencent ASR 和只读 Editorial Codex harness 仍是 Adapter/Agent Lane 后续项；本版没有使用 Codex 登录态。
4. 双封面仍是两个独立生图请求；Provider 自动切换解决可用性，不等价于 Master Art 本地派生的成本优化。
