# AI 编排需求理解

## 2026-08-24 10:07

### 背景与证据

PotatoFlow 已具备弹幕/字幕分析、投稿元数据、标签、分区和双尺寸封面生成能力，但当前实现仍以功能函数为中心，而不是以一次录播的 AI 作业为中心。实测账单截图显示，约 5 分 22 秒内产生 18 次文本模型调用，单次输入约 1.82 万至 2.06 万 token；只有少数请求命中 4,864 个缓存 token，多数请求没有缓存命中。这说明连接池复用正常并不等于提示词缓存有效。

当前主要问题如下：

1. 稳定规则、DOTA/TI 领域规则、房间自定义要求和本次证据混杂，房间级变量会改变系统提示词前缀。
2. `ai_metadata_request_slot` 是并发信号量，不是 RPM/TPM 限速器；SDK 内部重试和思考参数降级还可能形成不可见的额外请求。
3. `ai_request_ledger` 原先只能观测逻辑调用和部分 token，不能区分一个录播任务下的元数据、标签分区和不同封面作业，也没有记录缓存写入 token。
4. 元数据流程会执行 N 个批次摘要、简介补救、全局时间线筛选、最多三次标题、标签、内容画像、分区以及两次生图。单次调用失败还可能触发 JSON 模式回退或解析补救。
5. Chat Completions 请求完全无状态；系统中并不存在可管理的 API 会话。所谓“一个对话管理多个进程”实际是任务归因和调用编排混乱，不应通过把独立进程串进同一会话解决。
6. 双尺寸封面当前各调用一次图像模型。跨多个录播拼一张网格图再截图会降低单格分辨率，并扩大审核失败、构图串扰和裁切失败的影响范围。

### 目标

- 同一场景的稳定系统提示词形成可重复命中的缓存前缀。
- 每一次真实模型请求都经过同一跨进程 RPM 边界，并能独立记录成功、失败、重试、等待和 token。
- 一个录播任务拆分成明确的 AI 作业：`recording_metadata`、`recording_enrichment`、`cover_16x9`、`cover_4x3`；作业之间默认不共享会话。
- 房间级文案偏好和本次证据放在变量负载中，不能污染全局系统规则。
- 将每个录播的物理调用数、缓存读取/写入 token、输入 token、峰值 RPM、失败率、延迟和成本作为验收指标。
- 继续支持 OpenAI 兼容端点；只有官方 OpenAI 端点或用户显式确认兼容能力时，才发送供应商专用缓存参数。
- 不使用 Codex 登录状态、登录 token 或 ChatGPT 订阅作为 PotatoFlow 的运行时 API 凭证。
- AI 字幕处理必须成为录播任务中的独立可观察阶段；优先复用已有字幕，只有缺失时才允许 ASR，并将质检结果、来源和产物路径写入任务详情。
- B站合集“当前稿件已存在”（接口代码 `20080`）属于幂等成功，不得将已上传稿件标为失败或进入自动重试。
- 删除已经过期的 TI 2026 专用模式、赛程核验、提示词和视觉资源；普通 DOTA2 录播继续使用通用英雄、装备和 GSI 事实链。

### 非目标

- 本阶段不把所有 Chat Completions 一次性迁移到 Responses API。
- 本阶段不引入跨录播共享的长对话，也不把独立批次通过 `previous_response_id` 串联。
- 本阶段不默认启用多录播网格封面。
- 本阶段不存储原始提示词、字幕、弹幕或模型输出到调用账本。

### 验收口径

| 指标 | 当前基线 | MVP 目标 |
| --- | --- | --- |
| 稳定前缀缓存 | 多数请求 0，少数仅 4,864 token | 支持模型的元数据批次在热缓存后明显命中稳定系统前缀 |
| 物理请求可见性 | SDK 重试/降级可能漏记 | 每次实际 `chat.completions.create` 均单独记账 |
| RPM | 只有并发锁 | 所有进程按同一凭据和端点共享滑动窗口限制 |
| 作业归因 | 只有 task_id | 同时具备 task_id、job_id、job_purpose、scene_name |
| 动态偏好位置 | 插入 system prompt | 进入 user payload 的 `editorial_preferences` |
| 缓存观测 | cached_tokens | cached_tokens + cache_write_tokens + cache mode/key |
| AI 字幕 | 隐藏在直播数据整理中，缺少独立状态 | 已有字幕 → 持久化字幕 → 内嵌/平台字幕 → ASR 的渐进式来源链 |
| 合集重复加入 | `20080` 导致投稿任务失败 | 标记已跳过（已存在），继续后续评论与清理 |

### 统一 AI Control Plane 与内容证据层

新增需求不再是给现有单 Key 调用器增加零散分支，而是替换为统一控制面：`Provider Registry → Provider Router → policy + capability + quota → LLM / ASR / Image executor`。

1. 文本模型支持 4 个显式 Provider Profile，每个 Profile 独立配置 ID、Base URL、Key、模型、RPM 和场景；额度、鉴权或容量错误自动熔断并切换，旧全局配置只作为可关闭的迁移兼容层。
2. 图片模型同样支持 4 个 Profile 与参考图编辑能力声明；当前仅广告并执行已经实现的 OpenAI-compatible Images adapter，不能把尚未实现的 Gemini native adapter 伪装成可用。
3. ASR 免费池必须通过 Control Plane 的能力与 `free_only` 约束选择 Groq / Cloudflare，然后再由额度路由器执行；不得读取 Codex/ChatGPT 登录态。
4. TranscriptDocument 不是 SRT 附属品，而是进入私有 SQLite/FTS5 的第一类证据资产；必须保留原始文本与规范化文本，并提供按关键词和时间窗读取的渐进式接口。
5. OCR 作为录制结束后的独立低优先级步骤：固定周期/事件候选时间 → FFmpeg 串行抽帧 → 感知哈希去重 → 本地 RapidOCR → VisualEvidence。默认关闭，可在设置页显式启用；不调用远端 Vision API。
6. Provider Key、原始 Prompt 和原始证据不得写入调用账本；证据数据库和跨进程熔断数据库使用私有文件权限。
7. 所有新增流程必须在任务流程列表独立显示，至少包含 `ai_subtitle`、`evidence`、`visual_evidence`，并展示完成数量、缓存命中、跳过原因或非阻断失败。

验收标准：

- 文本主 Profile 返回 429 后同一逻辑请求由备用 Profile 完成，实际 Provider/模型进入物理请求账本；替换 Key 后不继承旧 Key 的熔断状态。
- 图片主 Profile 配额失败后自动切换；参考图模式只选择声明 `image.edit` 的 Profile。
- 已有字幕时 ASR 请求数为 0；无字幕且选择 `free_pool` 时只匹配 `billing_mode=free_only` 的 ASR。
- 同一 Transcript 重试入库不产生重复 FTS 记录；同一帧和 OCR 模型版本不重复推理。
- OCR 固定并发为 1，失败只把 `visual_evidence` 标记为 warning，不阻断投稿。

### AI 字幕缺失时的免费 ASR 与多凭据路由

补充上下文明确：ASR 不是默认事实源，也不能覆盖已经存在的 AI 字幕。系统必须先解析侧挂字幕、持久化 TranscriptDocument、内嵌字幕和平台字幕；全部缺失后才允许进入 ASR。

新增需求：

1. 增加显式 `free_pool` 模式，按 Groq Free、Cloudflare Workers AI Free 的顺序路由；一个提供商的本地额度或远端限流耗尽后自动切换下一个。
2. 支持多个提供商各自的 Key、Account ID、模型和额度配置，但不得轮换同一提供商的多个 Key 绕过组织级限制。
3. `free_pool` 必须是 `free_only`：禁止静默进入 OpenAI、Mistral 或其他付费 ASR；全部不可用时返回 `pending_free_quota`。
4. 免费额度台账必须跨进程原子预留，并覆盖音频秒、小时/日上限和 RPM；台账不得保存 Key。
5. VAD 后每个窗口可以选择不同提供商，但只要任一窗口因免费额度缺失而未完成，就不得输出看似完整的部分字幕。
6. Groq/Cloudflare 的额度数字作为可配置保守默认值，不硬编码为长期事实，设置页提示以供应商控制台为准。

验收标准：

- 已存在 `_AI字幕.srt` 时，免费 ASR Provider 的调用数仍为 0。
- Groq 返回 429 或本地额度不足时，同一窗口自动尝试 Cloudflare。
- 两个 Provider 都不可用时不调用任何付费端点，AI 字幕阶段显示 `pending_free_quota`。
- 日志、缓存、任务详情和 SQLite 额度台账均不出现 Groq/Cloudflare Key 明文。

## 2026-08-24 11:01

### v1.6.128 继续改进范围

v1.6.127 已能限制和观测真实请求，但 Prompt Cache 仍只降低重复前缀费用，不能减少逻辑请求数。本阶段优先处理重复任务恢复、自动重试、相同字幕批次和确定性分类造成的整次重复推理。

### 新增需求

1. 只有成功解析为合法 JSON 对象的结果才允许进入应用级缓存；超时、空响应、解析失败和创作型标题重试不得缓存。
2. 缓存键必须包含场景、Prompt 版本、provider bucket、模型、输出预算、温度、思考模式以及完整输入哈希；不得保存输入 Prompt、原始字幕、弹幕或 API key 作为索引明文。
3. Prompt 合同变化必须通过版本号自然失效，不能要求用户手工清库。
4. 人工“重新生成”必须同时旁路缓存读取和写入，保证得到新的候选且不污染自动流程缓存。
5. 低温度分类、录播批次摘要、字幕质检和字幕翻译可以缓存；标题创作、简介补救、JSON 修复和 AI 分段重试默认不缓存。
6. 支持按场景配置模型和最大输出 Token，分类任务可以使用更轻量模型，录播摘要仍可使用高质量模型。
7. 任务详情应显示逻辑调用、真实请求、请求放大率、应用缓存命中数、Prompt 缓存率、输入 Token 和成本。
8. 结果缓存保存在本机私有 SQLite 数据库。结构化结果可能包含生成译文，因此设置页必须明确披露；缓存不进入诊断包，不保存凭据。

### 验收标准

- 同一已注册场景、相同版本与输入连续执行两次时，第二次物理请求数为 0，账本记录 `application_cache_hit=1`。
- 修改模型、Prompt 版本、输入、温度或 Token 预算后不得命中旧结果。
- `off` 和人工旁路不读写缓存；`refresh` 不读旧值但会写入新值；`read-only` 只读取已有结果。
- 未注册场景保持原调用行为，不因本阶段改造产生隐式缓存。
