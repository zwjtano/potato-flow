## 技术方案概述

在录制结束后的 AI 弹幕分析阶段增加“赛果二次验证”步骤。PotatoFlow 仍以原始 XML 弹幕为第一证据，只在识别到 TI 2026 且恰好得到两支候选队伍时，低频调用 Liquipedia MediaWiki API。外部结果只用于确认或否定弹幕推断，不单独制造赛果；查询失败、匹配不唯一或证据冲突时继续使用中性标题，绝不阻塞投稿。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| HTTP | Python 标准库 `urllib.request` | 项目已使用，无需新增依赖 |
| 外部数据 | Liquipedia MediaWiki API | 免费、无需 API Key，适合录制结束后的低频校验 |
| 缓存 | state 目录 JSON 文件 | 同一系列只查询一次，重启后仍可复用 |
| 失败策略 | fail-open | 外部服务故障不影响弹幕处理、封面生成和投稿 |

## 架构设计

1. 弹幕层从 XML 中识别赛事、两支队伍、候选比分及明确的胜负词。
2. `ti2026_context` 生成标准化查询条件，不负责网络访问。
3. 新增 Liquipedia 客户端查询对应日期/队伍的 TI 比赛页面并提取已完成赛果。
4. 验证器对比队伍集合、比赛状态、BO 制和比分合法性，生成核验结论。
5. 标题与封面只消费核验结论；外部结果不能覆盖冲突的本地证据。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| `ti2026_context.py` | 队伍归一化、弹幕候选赛果、证据合并、强结论检查 | 无网络依赖 |
| `modules/liquipedia_result_verifier.py` | MediaWiki 请求、限流、缓存、响应解析 | `urllib.request`、state 路径 |
| `bridge.py` | 在标题生成前编排验证并写入 diagnostics/payload | 上述两个模块 |
| 设置页/config | 开关、联系邮箱、超时、缓存时长 | 现有配置系统 |

### 内部接口：查询并验证赛果

```json
  "cache_hit": false,
  "reason": ""

```

### 外部接口：MediaWiki API

- 请求方式：`GET`
- 基础路径：`https://liquipedia.net/dota2/api.php`
- 用途：搜索候选赛事/比赛页面，再读取结构化页面源或解析结果。
- 请求头：`User-Agent: PotatoFlow/<version> (<configured contact>)`、`Accept-Encoding: gzip`。
- 约束：进程级最短请求间隔 2 秒；`action=parse` 最短间隔 30 秒；优先缓存，单场默认缓存 24 小时。

## 数据模型

新增配置建议：

```python

    "liquipedia_contact": "",
    "liquipedia_timeout_seconds": 8,
    "liquipedia_cache_hours": 24,

```

缓存键由 `event + recording_date + sorted(canonical teams)` 计算；缓存文件保存原始响应摘要、解析结果和抓取时间，不保存 Cookie 或凭据。

## 核验规则

只有以下条件全部成立才返回 `confirmed`：

1. TI 上下文已激活，并且弹幕只识别出两支唯一队伍。
2. Liquipedia 候选比赛的赛事、日期和双方队伍全部匹配。
3. 比赛标记为已结束，比分符合 BO3 或 BO5 的终局比分。
4. 弹幕存在候选赛果；外部比分与弹幕的胜者/比分一致，或弹幕只缺少比分但存在足够的明确胜负证据。
5. 多个候选比赛时必须能以日期和比赛轮次唯一确定，否则 `not_found`。

`conflict`、`not_found`、超时、403、限流和解析变化都不得给标题增加“晋级、淘汰、横扫、夺冠”等词。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 查询时机 | 录制结束、弹幕解析之后 | 无实时性要求，调用极少且无直播剧透风险 |
| 证据地位 | Liquipedia 仅为二次验证 | 避免页面错配直接污染标题 |
| 自动查询范围 | TI 激活且恰好两队 | 防止泛 Dota 弹幕触发错误查询 |
| 联系信息为空 | 跳过查询并写 diagnostics | Liquipedia 要求可识别的 User-Agent，不能伪造邮箱 |
| 网络失败 | 中性标题继续流程 | 第三方服务不能成为投稿单点故障 |
| 页面解析 | 封装为独立适配器并保存 fixture 测试 | 页面结构变化时只修一处 |

## 实现计划

1. 为 XML 弹幕增加保守的候选比分、胜者和明确结果证据提取。
2. 实现 MediaWiki 客户端、限流、磁盘缓存及固定响应 fixture 测试。
3. 在 `bridge.py` 标题生成前调用验证器，把结果注入 `tournament_context.result_verification`。
4. 修改强赛果校验，使 `confirmed` 可作为弹幕证据的二次确认，但不能单独解锁结果词。
5. 设置页加入开关和联系邮箱，并在任务 diagnostics 展示查询状态、来源链接和失败原因。
6. 增加离线单元测试：确认、冲突、歧义、超时、缓存命中、API 结构变化及未配置联系人。

## 风险与验收

- 最大风险是 MediaWiki 页面模板变化；必须以保存的真实响应 fixture 测试解析器，并确保解析异常 fail-open。
- 正式编码前应先用 TI 2026 的一个真实已结束比赛页面做探测，确认 MediaWiki API 能稳定取得比分字段；如果只能依赖脆弱 HTML，则停止自动接入，改为人工粘贴 Liquipedia 比赛链接后验证。
- 验收标准：断网或 Liquipedia 故障时原流程完全不受影响；同场重试不重复请求；未经弹幕支持的外部赛果永远不能进入标题或封面。

## 一小时分段独立投稿方案（替代合并方案）

> 本节按用户确认的“不合并投稿”覆盖上一节中的自动拼接建议。每个一小时录制文件始终独立生成一个投稿任务，即使多个文件属于同一个 Match ID，也不合并视频、弹幕或任务。

## 核心原则

- 一个录制文件对应一个投稿任务，保持现有文件边界。
- 同一 Match ID 可以关联多个投稿，但每个投稿只能描述自身录像范围内发生的内容。
- 最终赛果只能用于包含终局的那一个分段，不能回填到前面的分段。
- 选手—英雄阵容可以在同局分段间复用；击杀数和KDA必须按分段事实权限处理。

## 场景一：文件前段比赛结束，后段没有新比赛

- 当前文件包含终局，因此可使用最终结果、系列赛比分、最终KDA和完整结果封面。
- 后续等待、聊天或复盘不影响结果权限。
- 标题聚焦已结束比赛；后半段没有新比赛就不制造第二主题。
- 底部显示该场最后一局的双方5v5阵容和最终击杀数。

## 场景二：同一局超过一小时并跨文件

### 第一段：比赛未结束

- 独立投稿，不等待第二段、不合并。
- 标题标记 `第1段` 或 `前60分钟`，只描述本段已核验的关键事件。
- 封面显示赛事阶段、BO制、`GAME N · 第1段`、双方队标和已确认阵容。
- 不显示最终系列赛比分、最终击杀、最终KDA、胜者、晋级或淘汰。
- 若录制期保存了可靠实时快照，可显示“截至本段结束”的击杀/KDA；否则隐藏对应数据框。

### 后续段：仍未结束

- 继续独立投稿，标记 `第2段`、`第3段`。
- 仍只使用本段结束时可知的快照，不使用未来终局。
- 标题避免重复第一段内容，只选择当前分段的新增团战、转折或选手表现。

### 包含终局的最后一段

- 独立投稿，标记 `收官段` 或实际分段编号。
- 可以使用最终系列赛比分、最终击杀、最终KDA和晋级/淘汰结论。
- 最终KDA属于比赛终局统计，可进入封面；但标题中的具体操作仍需当前分段弹幕支持，不能把第一段发生的操作写成本段事件。
- 封面底部使用同一 Match ID 的完整5v5阵容，中间显示最终本局击杀。

## 投稿命名示例

```text
第1段：TI瑞士轮第3轮｜LGD对阵Falcons第三局前60分钟，Topson卡尔守住关键团
收官段：TI瑞士轮第3轮｜第三局鏖战收官，LGD 2:1击败Falcons
```

封面层级：

```text
进行中分段：
TI 2026 · 瑞士轮第3轮 · BO3
Topson 卡尔关键守团
GAME 3 · 第1段
[LGD五英雄]   [无最终击杀框]   [Falcons五英雄]

终局分段：
TI 2026 · 瑞士轮第3轮 · BO3
Topson 卡尔掌控收官
GAME 3 · 收官段
LGD 2:1 FALCONS
[LGD五英雄] [本局击杀 41:36] [Falcons五英雄]
```

- 第一小时投稿绝不出现第63分钟才产生的最终赛果。
- 最后三分钟投稿可显示最终比分、击杀、KDA和晋级/淘汰结论。
- 两个投稿可以共享同一Match ID和双方阵容，但标题事件不会跨分段挪用。
- 前段比赛已结束、后段无新比赛的单文件仍生成完整结果版投稿。

## 一小时录制分段的比赛会话设计

### 问题定义

固定一小时录制文件与Dota比赛边界并不一致，至少存在两类常见情况：

1. 一小时文件前半段包含一场已经结束的比赛，后半段是等待、复盘或尚未开始下一场。
2. 单局比赛超过一小时，同一个 Match ID 横跨两个或更多录制文件。

因此新增 `match_session` 层，禁止直接假设“一个文件就是一局”。每个文件先切分或归属到比赛会话，再生成投稿任务。

## 场景一：前面比赛结束，后面没有新比赛

- 只要录像确实包含该局终局，就允许使用该局最终比分、KDA和结果型封面。
- 后半段等待或聊天不会取消前面已经完整发生的比赛结果。
- 标题聚焦已完成比赛，不写“下一场开始”或不存在的后续对阵。
- 封面使用已结束比赛的 Match ID、双方阵容和结果。
- 简介时间线可保留赛后复盘；纯等待段不作为标题依据。
- 若后半段出现另一场赛前BP但未开局，不把第二场阵容混入第一场封面。

判定条件：

```text
录像包含该局开始或主要过程
+ 录像末段前已出现终局证据
+ 外部 Match ID 标记该局结束
+ 后续没有另一场已开始的 Match ID
```

## 场景二：一局超过一小时

推荐做法不是分别生成两套独立投稿，而是将属于同一 Match ID 的连续录像片段合并为一个比赛任务：

```text
segment_1 (00:00-60:00, 比赛未结束)
segment_2 (60:00-63:06, 比赛结束)
→ match_session_8896731473
→ 一个完整投稿、一个结果标题、一张完整封面
```

归并条件必须全部满足：

- 同一直播间和同一录制会话。
- 相邻文件墙钟时间连续，允许最多120秒切片间隙。
- 双方队伍一致。
- 当前局次一致，或能取得同一个 Match ID。
- 第一段没有终局证据，下一段延续相同BP、选手或英雄上下文。

在第二段尚未生成前，第一段状态为 `waiting_match_completion`，暂不生成最终标题、封面和投稿。检测到终局后再合并处理。

## 等待上限与降级策略

- 一小时片段结束但比赛仍在进行：默认等待下一片段，最长120分钟。
- 新片段到达后立即重新判断，不固定睡眠轮询。
- 直播结束、等待超时或录制中断仍没有终局：降级为“比赛进行中 Part 1/Part 2”投稿，不使用最终赛果。
- 若后续片段在第一段已经投稿后才出现，不回改已发布视频；因此TI比赛模式应默认延迟首段投稿。
- 明确取得新 Match ID 时立即关闭上一比赛会话，禁止跨局合并。

## 合并实现

- 视频：相同编码参数时优先FFmpeg concat无损拼接；不一致时使用现有转码路径统一编码。
- XML弹幕：第二段时间戳整体加上第一段实际视频时长，再合并并去重。
- GSI/统计快照：保留原墙钟时间，合并时重算相对视频时间。
- Match ID：作为会话主键；Match ID未出现前使用“直播间＋双方＋局次＋相邻时间”临时键，取得ID后升级。
- 投稿幂等：一个 `match_session` 只能生成一个上传任务，防止两个一小时文件重复投稿同一局。

## 两种场景的最终封面

| 场景 | 主视觉 | 比分 | 底部阵容 | KDA |
|------|--------|------|----------|-----|
| 前半段比赛已结束，后半段等待 | 已结束比赛的突出选手＋英雄 | 最终系列赛/小局结果 | 已结束当局5v5 | 当局最终KDA |
| 同一局跨两个文件且已合并 | 合并后全局突出选手＋英雄 | 最终结果 | 同一Match ID的5v5 | 当局最终KDA |
| 同一局跨文件但等待超时 | 录像内关键选手＋英雄 | 仅已完成小局比分 | 有可靠阵容才显示 | 仅录像结束快照，否则隐藏 |

## 新增状态

```python
    "match_session_id": "temporary-or-match-id",
    "state": "waiting_match_completion|ready_complete|ready_partial",
    "segment_paths": [],

    "segment_end_china": [],
    "match_id": null,

    "next_match_started": false

```

## 验收标准

- 前半段已经完成一场、后半段没有比赛时，仍能生成该场的完整结果封面。
- 63分钟比赛切成60分钟＋3分钟时，只产生一个投稿任务，标题和封面覆盖完整比赛。
- 第一段关闭时不会提前上传，也不会倒灌当时尚未发生的最终结果。
- 不同 Match ID、不同局次或下一场BP不能被误拼到一起。

## 技术方案概述

为“比赛只进行了一半”增加独立的 `in_progress` 比赛状态。系统必须区分“外部赛果后来已经产生”和“当前录像是否包含比赛结束”：只有录像时间范围覆盖终局，最终比分、胜者、晋级或淘汰才允许进入该录像标题与封面；录像在比赛中途结束时，即使处理时已经能查到最终结果，也继续使用无剧透的进行中封面。

## 技术选型

| 类别 | 选择 | 理由 |
|------|------|------|
| 状态模型 | 显式比赛生命周期状态机 | 避免用 `0:0` 或接口缺失猜测状态 |
| 时间判断 | 中国录像起止时间对比比赛开始/结束时间 | 防止赛后处理给半场录像倒灌最终结果 |
| 数据来源 | 弹幕 XML + 结构化录像时间 + Liquipedia/OpenDota | 本地内容边界与外部事实交叉核验 |
| 等待策略 | 有上限的低频复查 | 既争取赛后数据，又不无限阻塞投稿 |

## 架构设计

比赛生命周期分为五种状态：

| 状态 | 含义 | 标题/封面权限 |
|------|------|---------------|
| `scheduled` | 尚未开始 | 只能写对阵、时间、阶段和赛制 |
| `live_unknown_game` | 已开赛但未取得 Match ID | 可写对阵和进行中，不写英雄、KDA或最终比分 |
| `live_game` | 已取得当前局阵容或实时快照 | 可写当前局次、双方英雄和截至录像结束的关键事件；不写终局结论 |
| `game_finished_series_live` | 当前小局已结束，系列赛未结束 | 可写该局胜负、当局KDA和当前系列赛比分；不写晋级、淘汰或系列赛胜者 |
| `series_finished` | 系列赛已结束 | 录像覆盖终局时可使用完整结果版模板 |

核心判断不是“查询时比赛是否结束”，而是：

```text
recording_end_china >= verified_game_end_china - tolerance
```

只有该条件成立，当前录像才被视为包含终局。容差建议 90 秒，用于直播延迟、文件时间取整和弹幕反应延迟；同时仍需录像末段弹幕出现基地告破、GG、获胜或系列赛结束等证据。

## 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| 比赛验证器 | 返回比赛状态、开始/结束时间、当前局与系列赛结果 | Liquipedia/OpenDota |
| 录像覆盖判断器 | 比较录像起止时间和比赛时间，决定可见事实上限 | 文件名时间、视频时长 |

| 封面策略 | 选择赛前、进行中、小局结束或系列赛结束模板 | 标题策略、英雄与比分数据 |

## 标题与封面规则

### 比赛进行一半、录像也在中途结束

- 标题优先描述录像内已发生的具体团战、选手表现或局势转折。
- 禁止写最终胜者、最终比分、晋级、淘汰、横扫或夺冠。
- 封面顶部仍显示赛事阶段和 BO 制。
- 中部显示 `GAME N`，系列赛只显示录像结束时已经完成的小局比分。
- 底部英雄阵容只有 Match ID、BP或可靠结构化数据确认后才展示。
- 中间击杀数只有录像结束时存在可靠快照时才展示，并标注为快照语义；没有快照则隐藏整个数字框。
- KDA只能使用录像结束时快照；赛后最终KDA不得回填到中途录像。

### 当前小局结束，但系列赛仍在继续

- 可以写该局胜负和该局选手最终KDA。
- 可以显示当前系列赛比分，例如 `LGD 1:0 Falcons`。
- 不得写系列赛胜者、晋级或淘汰。
- 下一局阵容尚未产生时，底部仍显示刚结束这一局，并明确 `GAME N`。

### 处理期间等待

- 录像结束后先立即解析本地弹幕。
- 若末段存在明确 GG/获胜证据但 Match ID 尚未写入，最多等待 15 分钟，每 2 分钟复查一次。
- 若录像显然在比赛中途结束，不等待最终赛果，直接生成进行中版本。
- 等待超时后继续投稿，第三方接口不得成为阻塞点。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 赛后API结果能否用于半场录像 | 不能 | 结果不在当前视频内容范围内，会剧透并造成标题与内容不符 |
| 中途录像是否显示实时击杀/KDA | 仅有可靠快照时 | OpenDota赛后数据不能代表录像结束瞬间 |
| 是否等待比赛结束 | 只在录像包含终局迹象时短暂等待 | 减少接口更新延迟，又避免无意义阻塞 |
| 分段录像的最终结果 | 只给包含终局的分段 | 每个视频标题必须描述自身内容 |
| 缺失数据 | 隐藏对应模块 | 不使用占位比分或AI猜测 |

## 实现计划

1. 从文件名和视频时长计算录像中国时间起止区间。
2. 扩展比赛验证器，保存每局开始、时长、结束时间及系列赛完成状态。
3. 实现录像覆盖状态分类函数及边界测试。
4. 增加“进行中”和“小局结束、系列赛继续”两套标题/封面提示。
5. 将强赛果校验改为同时要求外部结果和录像覆盖终局。
6. 测试凌晨跨日、直播延迟、录像分段、赛后重试和接口更新延迟。

## 风险与验收

- OpenDota通常提供赛后最终数据而不是录像结束瞬间快照，因此没有GSI或录制期实时快照时，中途击杀与KDA必须隐藏。
- 直播流可能比DotaTV/API延迟，单靠墙钟时间仍会剧透；必须再检查录像末段弹幕终局证据。
- 验收标准：同一场比赛的前半段录像永远不会因赛后重试而获得最终结果；只有包含终局的最后分段能使用结果型标题和完整结果封面。

## 整段录播无赛果的标题与封面方案

### 场景定义

整段录像内已经识别到 TI 对局，但截止录像结束时间，小局仍未结束。Valve 实时快照可提供当时的局内时间、击杀、英雄和选手数据，但不存在该局胜者或最终赛果。

### 标题结构

```text
【TI2026·赛事阶段 BO制】队伍A vs 队伍B G局次｜录像内核心看点｜鏖战未决
```

示例：

```text
【TI2026·瑞士轮 BO3】LGD vs Falcons G2｜Ame水人高地攻防｜鏖战未决
```

标题规则：

- 必须包含赛事阶段、BO制、双方队伍和当前局次。
- 核心看点只使用录像中已经发生并能由弹幕或实时快照确认的内容。
- 末尾统一使用“鏖战未决”，明确本段不含终局。
- 不写最终比分、最终击杀、获胜、翻盘、晋级、淘汰、横扫或赛点兑现。
- 实时击杀和截止KDA默认不塞入标题，避免标题过密；只放在封面。

### 封面结构

```text
顶部：TI2026｜赛事阶段｜BO制
主视觉：双方队伍对抗，突出一名已核验选手及其真实英雄
选手信息：选手名 + 英雄名 + 截止KDA
中央信息：GAME N｜鏖战未决
比分区域：录像截止 28:31
底部：两边各5名已选择英雄，按实际阵营排列
```

封面规则：

- 击杀数字必须标注“录像截止”，不能写“本局击杀”，防止被理解成最终数据。
- KDA必须标注“截止KDA”，数据取录像结束前最后一份 Valve 快照。
- 系列赛比分只显示录像开始前已经完成的小局比分，并标注“系列赛当前”；不显示当前未结束小局的胜负。
- 没有可靠实时快照时，整块击杀数字和KDA隐藏，不显示 `0:0` 或问号占位。
- 英雄只使用 Valve 快照确认的十名英雄；缺失阵容时隐藏底部英雄条。
- 禁止胜利方高亮、奖杯、不朽盾、晋级箭头以及任何终局视觉语言。

### 数据截取

最后一份满足 `snapshot_wall_time <= recording_end` 的 Valve 快照作为封面数据；所有晚于录像结束时间的快照均不得回填。该场随后产生的最终结果也不改变本段标题和封面。
