## 技术方案概述

Windows 版继续复用 Flask/Python、Rust `recorder-core` 和 FFmpeg，不复制一套业务代码。新增明确的跨平台运行契约：Python 统一解析解释器与录制二进制，Rust 文件名模板同时保留 POSIX 根目录和 Windows 盘符，进程生命周期按平台分别实现。以 Windows 11 x64、Python 3.11、Rust MSVC、FFmpeg x64 为本机验收环境。

## 技术选型

| 类别 | 选择 | 理由 |
|---|---|---|
| Web/业务 | 现有 Flask + Python 3.11 | 与 CI 和当前业务保持一致 |
| 录制核心 | 现有 Rust `biliup-cli`，MSVC Release 构建 | 不维护第二套录制逻辑 |
| 媒体处理 | 项目 FFmpeg/ffprobe | 支持 libass 与 AMD AMF，路径可控 |
| 数据目录 | Windows 默认使用用户“文档/PotatoFlow/recordings” | 用户可直接找到录制文件，页面自定义目录仍优先 |

## 架构设计

1. Windows Web 进程只负责配置、状态和任务编排。
2. 录制 worker 使用 `biliup.exe recorder`，通过绝对配置路径和状态文件通信。
3. 配置生成器只输出完整绝对路径；Rust 清洗文件名时保留 `C:/` 盘符根。
4. 后处理始终使用当前运行中的 `sys.executable`，不再拼接 Linux `.venv/bin/python`。
5. 进程启动与停止由平台适配层处理；Windows 不调用 `os.killpg`。
6. 编码器通用探测使用硬件兼容的小画面，真实烧录保持源分辨率，包括 2160p。

## 模块划分

| 模块 | 职责 | 修改范围 |
|---|---|---|
| Windows 运行时解析 | Python、FFmpeg、`biliup.exe` 路径 | `runtime_environment.py`、录制/投稿管理器 |
| 录制配置生成 | 输出目录、bridge 命令、YAML | `live_recorder_manager.py` |
| Windows 路径契约 | 保留盘符并清洗目录分量 | Rust `server/common/util.rs` |
| 进程生命周期 | Windows worker 安全启动/停止 | `live_recorder_manager.py` |
| 编码器检测 | CPU/AMD/NVIDIA/Intel 通用可用性探测 | `danmaku_pipeline.py` |

## 接口设计

现有 Web API 保持兼容：

- `GET /healthz`：验证 Web 版本。
- `GET /live-recording/status`：返回 `binary_ready`、worker PID、当前文件及大小。
- `POST /live-recording/start|stop`：控制指定直播间。
- `GET /api/encoding-capabilities?purpose=danmaku&refresh=on`：强制刷新编码器通用检测。

不增加平台专属前端接口，Windows 差异收敛在运行时与录制核心内部。

## 数据模型

不改数据库结构。文件路径必须满足：

- `recordings_path` 是绝对、可写目录。
- `filename_prefix` 在 Windows 生成 `C:/...` 语义，在 Linux 生成 `/...` 语义。
- 状态中的 `current_file` 必须能够解析回真实文件并报告增长中的大小。

## 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| Windows 是否单独分叉 | 不分叉 | 避免功能漂移，仅隔离平台边界 |
| Windows 路径修复位置 | Rust 清洗器保留盘符 | 视频与 XML 共用同一文件模板，修复最完整 |
| Python 后处理解释器 | `sys.executable` | 同时适配 venv、系统 Python 和打包 EXE |
| 进程停止 | 平台分支 | Windows 没有 POSIX process group 信号语义 |
| 误写文件 | 验证后迁移，不删除 | 保护已有录制数据 |
